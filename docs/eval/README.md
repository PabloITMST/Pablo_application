# 재현 점검(🔎) 정량 평가

Pablo의 재현 점검이 "코드가 논문에서 벗어난 곳"을 얼마나 찾고, 얼마나 잘못 짚는지 잰 기록입니다.
같은 모델에 Pablo 없이 그냥 물었을 때와도 비교했습니다.
결과 원본은 같은 폴더에 있습니다.
- `audit-bench-<날짜>.*`: Pablo 점검
- `audit-bench-<날짜>-plain-results.json`, `compare-<날짜>.*`: 비교군

## 질문

논문 조건 목록이 주어졌을 때, 점검이 다음을 해내는가?
1. 작업 폴더의 코드·설정·로그 가운데 조건을 어긴 곳을 찾는다(탐지율).
2. 조건을 따르는 곳을 어겼다고 하지 않는다(오탐률).
3. 그 위치(파일:줄)를 맞힌다(위치 정확도).
4. 같은 모델에 논문만 주고 "다른 곳을 찾아줘"라고 할 때보다 무엇이 나은가, 무엇이 모자란가(비교군).

## 방법

| 항목 | 내용 |
|---|---|
| 논문 | LinearRAG (arXiv 2510.10114v4) |
| 조건 | 코드로 따르거나 어길 수 있는 조건 17개 + 논문에 없는 설정 1개(시드). 문장과 인용은 실제 `spec` 추출 결과에서 가져와 고정했고, 인용은 모두 원문 쪽에 고정됩니다(`tests/eval/linearrag_conditions.json`). |
| 바탕 폴더 | 17개 조건의 값과 설정을 모두 따르는 재현 코드 7개 파일(`tests/eval/repro_base/`): config, 전처리(구두점 분할·spaCy), 그래프, 검색(PageRank), 평가, 실행, 로그. 주석에 논문 용어를 넣지 않았습니다. 점검이 주석이 아니라 코드를 보고 판단하는지 보려는 것입니다. 방법 수준에서는 논문의 뼈대만 옮긴 코드입니다(아래 "비교군" 참고). |
| 심은 어긋남 | 18종(`tests/eval/audit_bench.py`의 `CATALOG`). 아래 표 참고. |
| 변형 | 씨앗을 고정한 무작위로 어긋남 1–3개씩 담은 8개 + 깨끗한 1개. 한 변형 안에서는 같은 조건이나 같은 코드 위치를 두 번 건드리지 않습니다. 어긋남 하나가 다른 조건을 흐리게 만들면 그 조건은 그 변형에서 채점하지 않습니다(예: PageRank를 없애면 감쇠 계수가 쓰이지 않음). |
| 실행 | 앱에서 사용자가 하듯 변형마다 작업 폴더를 바꾸고 🔎 재현 점검을 누릅니다. 변형마다 새 대화(thread)이고, 파일은 읽기만 합니다(`npm --prefix desktop run check -- --audit-bench 8 7`, 실제 ChatGPT 계정). |
| 채점 | `python tests/eval/audit_bench.py score <results> <truth> <keys>` |

심은 어긋남 18종:

| 종류 | 어긋남 |
|---|---|
| 설정값 | top_k 5→10, 임베딩 all-mpnet-base-v2→all-MiniLM-L6-v2, LLM gpt-4o-mini→gpt-4o, 감쇠 0.85→0.5, δ 4→2, λ 0.05→0.5, 데이터셋에서 Medical 빼기, 문항 1000→500, split validation→test |
| 코드 | 설정을 무시한 `k = 10`, spaCy NER→정규식, 구두점 분할→50단어 고정 창, 그래프에서 문장 노드 빼기, PageRank→차수 점수, Contain 지표 함수 지우기, Medical도 두 지표로 채점 |
| 결과 로그 | 2Wiki GPT 정확도 63.70→58.10, Contain 정확도 70.20→64.35 |

### Pablo의 확인 (점검 답의 파일:줄을 Pablo가 직접 읽음)

0.8 Phase A의 `verify`(`desktop/where.js`)가 모델이 댄 파일:줄을 열어, 적힌 코드가 거기 있는지와 논문 값이 판정과 맞는지 봅니다.
`score`는 저장된 확인 결과를 믿지 않고, 변형을 씨앗에서 다시 만들어 지금의 `where.js`로 다시 계산합니다. 규칙이 바뀌면 숫자도 따라옵니다.

- **짚은 어긋남 18건, 따르는 조건 131건:** 모두 확인됨(verified)입니다.
  - 답을 받던 때의 규칙으로는 따르는 조건 37건이 거짓 경고였습니다.
  - 28건은 "punctuation"처럼 코드에 글자로 없는 개념어 값이었고, 9건은 `preprocess.py:6,15`처럼 줄을 여러 개 적은 위치였습니다.
  - Phase A에서 두 규칙을 고쳤습니다(c94431c, 998fe44).
- **대조 (답을 다른 폴더에 대고 확인):** 각 변형의 답을 다음 변형의 폴더에서 확인하면, 짚은 어긋남 18건 중 16건이 확인에 실패합니다(못 찾음 15, 줄이 옮겨짐 1).
  - 남은 2건은 두 폴더에 똑같이 있는 줄을 인용했습니다(`for ent in entities(text):` 등). 어긋남이 그 줄 주변에서 무언가가 빠진 것이기 때문입니다.
  - 확인은 "인용이 그 자리에 있는가"를 볼 뿐, 판정이 옳은지는 보지 않습니다.
- **실제로 일어난 사고:** 첫 실행은 앱 버그로 9개 변형 모두 첫 폴더를 읽고 답했습니다(탐지율 0%).
  - 그 답을 각 변형 폴더에 대고 다시 확인하면, 놓친 어긋남 18건 중 15건에 Pablo가 경고(못 찾음·줄 옮겨짐)를 붙입니다.
  - 모델이 엉뚱한 폴더를 보고 "따름"이라고 답해도, 사용자는 대부분의 경우 경고를 받습니다.

## 비교군: 같은 모델에 그냥 묻기 (2026-10-13)

연구자가 범용 코딩 에이전트로 할 법한 일을 그대로 시켰습니다.

| 항목 | Pablo 재현 점검 | 그냥 묻기 |
|---|---|---|
| 입력 | 조건 17개 + 논문 인용·쪽 + 논문에 없는 설정 1개 | 논문 본문 전체(쪽 번호 포함, 74,001자) + "코드·설정·로그를 읽고 논문에 적힌 실험 조건과 다르게 구현되었거나 빠진 곳을 모두 찾아 주세요" |
| 답 | 조건마다 따름/다름/없음/판단 못 함/코드가 정함 + 파일:줄 + 그 자리 코드 | 다른 곳마다 무엇·어디(파일:줄)·논문·코드 |
| 공통 | 같은 변형 9개, 같은 모델(gpt-5.6-luna), 읽기 전용, JSON 스키마로 받은 답, 변형마다 새 thread | |

채점은 두 시스템에 같은 규칙을 씁니다(`audit_bench.py compare`).
- **찾음:** 보고가 심은 어긋남의 파일:줄(±2)을 짚고, 코드가 무엇을 하는지 말한 부분에 바뀐 내용이 나와야 합니다(`SAYS`: "MiniLM", "delta=2", "500" 등).
  - 열 줄 넘는 범위는 줄을 짚은 것으로 보지 않습니다.
  - 위치만으로 채점하면 두 시스템 모두 18/18입니다.
  - 그러나 그냥 묻기의 한 건은 같은 줄을 짚었지만 다른 이야기(검색 품질 지표가 없음)였습니다.
  - 심은 어긋남 18건마다 위치가 맞은 보고(31건)를 사람이 읽고 내린 판단(17건 찾음, Medical 1건 못 찾음)과 이 규칙의 판단이 같습니다.

### 이 비교가 말하는 것

1. **작은 저장소의 단일 지점 어긋남은 그냥 물어도 거의 다 찾습니다(17/18).** 이 벤치마크의 심은 어긋남만으로는 Pablo의 탐지율 우위가 1건입니다. 그 1건(Medical 채점 규칙)은 논문의 평가 설명 깊숙이 있는 조건이고, 조건 목록이 그것을 미리 뽑아 두었기 때문에 Pablo가 찾았습니다.
2. **Pablo의 차이는 답의 꼴에 있습니다.**
   - **빠짐없음을 말합니다.** 조건마다 판정을 주므로, 보고가 없다는 것은 "보고 따름"이라는 뜻입니다. 그냥 묻기는 무엇을 확인했는지 말하지 않습니다.
   - **논문이 정하지 않은 설정을 짚습니다.** 시드처럼 재현 보고서에 적어야 할 "코드가 정한 값"을 9/9 짚었고, 그냥 묻기는 한 번도 말하지 않았습니다.
   - **읽을 양이 적습니다.** 19건 대 143건입니다. 그냥 묻기에서 심은 어긋남은 변형당 보고 약 16건 가운데 1–3건입니다.
   - **근거와 확인이 붙습니다.** 판정마다 원문 쪽 인용이 붙고, Pablo가 파일:줄을 직접 확인합니다. 그냥 묻기의 답은 사람이 하나하나 열어 봐야 합니다.
3. **Pablo가 모자란 곳도 드러났습니다. 방법의 충실도를 보지 않습니다.**
   - Pablo는 δ를 "따름"으로 판정했습니다. 값(4)은 맞기 때문입니다. 그러나 코드는 δ를 임계값이 아니라 hop 수로 씁니다.
   - 조건이 값과 설정 수준에 머물러 있어서, 연구자가 꼭 알아야 할 방법 수준의 차이 84건을 하나도 말하지 않았습니다.
   - 그냥 묻기는 이것을 일관되게 잡았습니다.

## 이 숫자가 말하는 것과 말하지 않는 것

말하는 것:
- 조건 목록과 작은 저장소가 주어지면, 점검은 설정·코드·로그에 심은 단일 지점 어긋남을 놓치지 않습니다.
- 따르는 코드를 어겼다고 하지도 않습니다. 위치도 정확합니다.
- 주석에 논문 용어가 없어도 코드 동작(분할 방식, 랭킹 방식, 지표 계산)을 보고 판단합니다.
- Pablo의 확인은 엉뚱한 폴더·옛 상태에 대한 답을 대부분 잡습니다(대조 16/18, 실제 사고 15/18).

말하지 않는 것(한계):
- **쉬운 설정입니다.** 저장소가 7개 파일로 작고, 어긋남이 한 곳에 뚜렷합니다. 실제 저장소는 수십~수백 파일이고, 어긋남은 여러 곳에 흩어지거나 미묘합니다. 비교군이 17/18을 찾은 것도 이 쉬움 때문일 수 있습니다.
- **바탕 폴더는 값 수준에서만 논문을 따릅니다.** "깨끗한 변형"은 17개 조건에 대해 깨끗하다는 뜻이고, 방법 수준에서는 위의 84건만큼 논문과 다릅니다.
- **조건은 고정했습니다.** 이 평가는 "조건 → 코드 대조"만 잽니다. 조건 추출 품질은 따로 쟀습니다(LinearRAG에서 25개 고정, 0개 탈락). 두 단계를 이어 잰 숫자는 아직 없습니다.
- **반복이 없습니다.** 모델 하나, 씨앗 하나, 변형마다 1회입니다. LLM 판단의 흔들림(분산)을 재지 않았습니다.
- **같은 폴더에서 나온 항목입니다.** 오탐 0/131은 9개 폴더의 항목 131개라 서로 독립이 아닙니다.
- **"심은 것 밖의 보고"의 분류는 한 사람이 읽은 것입니다.** 키워드로 묶고 모두 읽었지만, 두 번째 판정자는 없습니다.

   - 그 뒤 이 벤치마크로 다시 잽니다. 이번 비교군의 방법 수준 묶음 9개가 정답 후보입니다.
2. **어려운 어긋남:** `[:k+1]` 같은 off-by-one, 튜닝 루프가 test split을 쓰는 데이터 누수, 주석은 5인데 코드는 10, CLI 기본값이 설정을 덮어씀, 시드를 두고도 쓰지 않음, 다른 필드로 지표 계산. 그냥 묻기와의 차이가 여기서 커지는지 봅니다.
3. **반복:** 씨앗 3개 × 모델 2개(luna, sol), 두 시스템 모두. 평균과 범위를 보고합니다.
4. **현실 크기 저장소:** 공식 LinearRAG 구현(라이선스 확인 뒤)에 어긋남을 심습니다.
5. **추출부터 끝까지:** 고정 조건 대신 매번 `spec`으로 뽑은 조건으로 점검합니다. `SAYS`처럼 키워드로 정답을 맞추는 채점을 조건에도 씁니다.

## 다시 돌리기

```bash
python tests/eval/test_audit_bench.py                      # offline: 생성기·채점기·확인 재계산 (node 필요)
npm --prefix desktop run check -- --audit-bench 8 7        # 실제 계정, 약 7분 (앱으로 먼저 로그인)
npm --prefix desktop run check -- --audit-bench 8 7 --plain   # 비교군, 실제 계정, 약 11분
python tests/eval/audit_bench.py score docs/eval/audit-bench-2026-10-13-results.json docs/eval/audit-bench-2026-10-13-truth.json docs/eval/audit-bench-2026-10-13-keys.json
python tests/eval/audit_bench.py compare docs/eval/audit-bench-2026-10-13-results.json docs/eval/audit-bench-2026-10-13-plain-results.json docs/eval/audit-bench-2026-10-13-truth.json
```

- `state`와 `baseline-prompt`(실행기가 부름)는 `build/venv`의 Python이 필요합니다(pypdf). `PATH` 앞에 `build/venv/Scripts`를 둡니다.
- `score`는 확인을 다시 계산할 때 node를 씁니다. node가 없으면 저장된 값을 씁니다(`--saved-checks`로 강제).
- 실제 계정 점검은 한 번에 하나만 돌립니다. 같은 로그인 정보를 두 프로세스가 갱신하면 연결이 끊길 수 있습니다.
- 첫 실행에서는 9개 변형이 모두 첫 폴더를 점검해 탐지율 0%가 나왔습니다. 작업 폴더를 바꿔도 같은 thread를 쓰던 앱 버그였고, 고쳤습니다(`desktop/agent.js`). 지금은 두 실행기 모두 변형마다 새 thread와 그 폴더인지 확인합니다.
