# 재현 점검(🔎) 정량 평가

Pablo의 재현 점검이 "코드가 논문에서 벗어난 곳"을 얼마나 찾고, 얼마나 잘못 짚는지 잰 기록입니다.
같은 모델에 Pablo 없이 그냥 물었을 때와도 비교했습니다.
결과 원본은 같은 폴더에 있습니다.
- `audit-bench-<날짜>.*`: Pablo 점검 (값 조건 17개)
- `audit-bench-<날짜>-plain-results.json`, `compare-<날짜>.*`: 비교군
- `audit-bench-<날짜>-method3.*`, `compare-<날짜>-method.*`: 방법 조건을 더한 Pablo 점검과 세 시스템 비교. `-method`, `-method2`는 프롬프트를 고치기 전의 실행입니다.
- `audit-bench-<날짜>-hard.*`, `compare-<날짜>-hard.*`: 처음 보는 어긋남(프롬프트를 고칠 때 보지 않은 12종)
- `audit-bench-<날짜>-e2e*`, `compare-<날짜>-e2e.*`: 실제 추출 조건으로 끝까지 잰 기준선(카드에 펼쳐지는 행)

## 요약

- **처음 보는 어긋남에서 탐지는 같은 모델에 그냥 물을 때와 비슷합니다.** Pablo 11/12, 그냥 묻기 10/12입니다.
  - 방법 수준의 차이는 그냥 묻기가 더 많이 짚습니다(52/56 대 32/56).
  - 프롬프트를 고친 세트의 18/18·오탐 0/131은 그 세트에 맞춰진 숫자입니다.
- **Pablo가 나은 점은 답의 꼴입니다.** 읽을 보고가 절반 이하이고(50 대 119), 판정마다 원문 쪽 근거가 붙고, Pablo가 파일:줄을 직접 확인합니다. 시드처럼 논문이 정하지 않은 설정도 짚습니다.
- **실제 추출 조건으로 끝까지 재면 카드당 13~15행이 펼쳐집니다.** 그중 코드에서 고칠 것이 절반쯤이고, 약 3~4행은 잡음입니다.
  - 조건 종류 표시는 서술 사실을 점검에서 뺐습니다. 하지만 지금의 병목은 추출입니다.
  - 추출할 때마다 빠지는 조건이 달라(NER, 감쇠 계수) 그 어긋남을 놓칩니다.
  - 표를 잘못 읽은 결과 조건 하나는 모든 폴더에 거짓 "다름"과 틀린 논문 값을 남겼습니다.
- **아직 모르는 것과 고칠 것:**
  - 모르는 것: 반복했을 때 판정이 같은지, 큰 저장소에서 어떤지.
  - 고쳤고 실측으로 확인한 것:
    - 서술 사실이 점검에 섞이는 것(bc214e8·8f48e1a): e2e2에서 접힌 "판단 못 함"이 카드당 4.9에서 0.3으로 줄었습니다.

## 질문

논문 조건 목록이 주어졌을 때, 점검이 다음을 해내는가?
1. 작업 폴더의 코드·설정·로그 가운데 조건을 어긴 곳을 찾는다(탐지율).
2. 조건을 따르는 곳을 어겼다고 하지 않는다(오탐률).
3. 그 위치(파일:줄)를 맞힌다(위치 정확도).
4. 같은 모델에 논문만 주고 "다른 곳을 찾아줘"라고 할 때보다 무엇이 나은가, 무엇이 모자란가(비교군).

### 이 비교가 말하는 것

1. **작은 저장소의 단일 지점 어긋남은 그냥 물어도 거의 다 찾습니다(17/18).** 이 벤치마크의 심은 어긋남만으로는 Pablo의 탐지율 우위가 1건입니다. 그 1건(Medical 채점 규칙)은 논문의 평가 설명 깊숙이 있는 조건이고, 조건 목록이 그것을 미리 뽑아 두었기 때문에 Pablo가 찾았습니다.
2. **Pablo의 차이는 답의 꼴에 있습니다.**
   - **빠짐없음을 말합니다.** 조건마다 판정을 주므로, 보고가 없다는 것은 "보고 따름"이라는 뜻입니다. 그냥 묻기는 무엇을 확인했는지 말하지 않습니다.
   - **논문이 정하지 않은 설정을 짚습니다.** 시드처럼 재현 보고서에 적어야 할 "코드가 정한 값"을 9/9 짚었고, 그냥 묻기는 한 번도 말하지 않았습니다.
   - **읽을 양이 적습니다.** 19건 대 143건입니다. 그냥 묻기에서 심은 어긋남은 변형당 보고 약 16건 가운데 1–3건입니다.
   - **근거와 확인이 붙습니다.** 판정마다 원문 쪽 인용이 붙고, Pablo가 파일:줄을 직접 확인합니다. 그냥 묻기의 답은 사람이 하나하나 열어 봐야 합니다.
3. **Pablo가 모자란 곳도 드러났습니다. 방법의 충실도를 보지 않습니다.**
   - Pablo는 δ를 "따름"으로 판정했습니다. 값(4)은 맞기 때문입니다. 그러나 코드는 δ를 임계값이 아니라 hop 수로 씁니다.
   - 조건이 값과 설정 수준에 머물러 있어서, 연구자가 꼭 알아야 할 방법 수준의 차이 84건을 하나도 말하지 않았습니다.
   - 그냥 묻기는 이것을 일관되게 잡았습니다.
   - 이 빈틈을 메운 결과는 바로 아래 "방법 조건을 더한 뒤"에 있습니다.

무엇을 바꿨나:
- **`spec`이 방법 조건을 뽑습니다.** 값만이 아니라 그 값이 무엇을 정하는지, 점수를 어떻게 계산하는지, 단계 사이에 무엇이 넘어가는지를 뽑습니다. 예: "δ는 4이다"가 아니라 "관련성 점수가 임계값을 넘는 entity만 남긴다". 인용은 다른 조건처럼 원문 쪽에 고정됩니다.
- **점검이 방법 조건을 코드가 하는 일로 판정합니다.** 값 조건은 실행에서 실제로 쓰이는 값으로 판정합니다.

- 바탕 폴더에서의 정답은 코드를 읽고 붙였습니다(`base`).

- **"심은 것 밖의 보고"의 분류는 한 사람이 읽은 것입니다.** 키워드로 묶고 모두 읽었지만, 두 번째 판정자는 없습니다.
- **방법 조건의 정답도 한 사람이 붙였습니다.** 바탕 폴더 코드를 읽고 붙였고, 판정이 갈릴 수 있는 1개(Tri-Graph)는 채점하지 않았습니다.
- **주제 집계(`THEMES`)는 표현 규칙입니다.** 보고가 하는 말에 주제별 표현이 나오는지로 셉니다. Pablo의 노트가 "delta만큼 반복"처럼 다른 말을 쓴 경우를 보고 규칙을 넓혔습니다. 규칙이 놓친 표현이 더 있을 수 있습니다.

   - 기준선 뒤에 바뀐 것이 종류 표시만은 아닙니다. 차이를 원인별로 나눠 셉니다.
